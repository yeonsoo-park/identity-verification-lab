# 8. 카카오뱅크 인증서 공개 가이드 참고 내역

- 출처: https://auth.kakaobank.com 의 공개 페이지만 읽었습니다(2026-11-02 기준). 읽은 페이지는 정책 및 공통가이드, API별 가이드(접근토큰발급, 본인확인), 오류코드, 디자인가이드입니다.
- 카카오뱅크 API 서버(개발·운영)에는 **접속하지 않았습니다**. 제휴 계약도 없고 credential도 없습니다.
- 이 문서는 **설계 방식을 배우려는 목적**으로 정리했습니다. 실제 연동 규격을 대신하지 않습니다.

## 8.1 공개 가이드에서 읽은 흐름 구조

1. **접근토큰 발급** `POST /api/v1/corp/auth`
   - 요청: 이용기관 ID와 credential
   - 응답: `access_token`, `expire_dttm`
2. **본인확인 요청** `POST /api/b2b/v1/identification`
   - 인증 방식(`app_invoke_method`)을 고릅니다: 앱 푸시, 앱투앱, 표준 웹(STD_WEB), QR
   - 응답: `trx_key`, `composite_key`, `expire_dttm`. 표준 웹 방식이면 `standard_web_url`도 옵니다
   - 표준 웹 방식에서 인증이 끝나면 `client_callback_url?composite_key=...`로 돌아옵니다
3. **결과 요청(polling)** `POST /api/b2b/v1/polling/mandatory/{composite_key}`
   - 결과는 `response_code`로 판단합니다
   - 콜백 방식으로 결과를 받는 것도 선택할 수 있습니다
4. **결과코드 체계**: 정상, 대기, 사용자 취소, 사용자 응답 없음, 가입자 불일치, 존재하지 않는 트랜잭션, 토큰 만료, 서버 통신 오류 등으로 의미를 나눕니다
5. **정책**
   - 통신은 HTTPS(TLS 1.2 이상)를 씁니다
   - 요청과 결과에 개인정보가 들어가면 AES로 암호화합니다
   - 결과에는 전자서명(PKCS#7)이 붙습니다
   - 서버 간 통신에 방화벽(IP) 허용이 필요합니다

## 8.2 이번 실습에 반영한 것

| 공개 가이드의 구조 | 실습 반영 | 위치 |
|---|---|---|
| 접근토큰 → 요청 → 결과 조회 3단계 | 같은 3단계로 구성. 서버가 토큰을 캐시하고, 만료되면 재발급 | `MockIdentityProviderClient` |
| `composite_key`로 결과 조회 | `provider_transaction_id`로 저장하고 조회에 사용 | B2·B3 API |
| 요청마다 `expire_dttm`(만료 일시) | 모의 기관도 만료 시각을 응답. 서비스는 별도로 자체 유효시간(`expires_at`)도 관리 | `identity_verifications.expires_at` |
| 표준 웹 + `client_callback_url` 복귀 | 모의 표준창 → 데모 화면로 303 복귀 | B5 |
| 복귀할 때 결과 대신 키만 전달 | 복귀 URL에는 `verificationId`만 담고, 결과는 서버가 조회 | B5, A2 |
| `response_code`로 결과 의미 판단 | `MV0000`/`MV0100`/`MV1000`/`MV1001`/`MV1002`/`MV9xxx`로 의미를 나눔. 의미를 알 수 없는 응답은 "확정 불가"로 처리 | `MockIdentityProviderClient#toResult` |
| "사용자 응답 없음(유효시간 내 미진행)" 코드 | 만료(`MV1001`)를 명시적인 결과로 다룸 | 모의 서버 |
| 개인정보 최소화 원칙 | 실습에서는 개인정보를 아예 보내지도 받지도 않음 | B2 요청 필드 |
| 결과의 전자서명(`signed_data`, PKCS#7) | 형식을 단순화해 구현. 원문·서명값·서명자 인증서를 분리하고, 서버가 Root CA로 체인과 서명을 검증 | [41-pki.md](41-pki.md), `ResultSignatureVerifier` |
| `client_callback_url` (https 필수) | 등록된 URL만 허용(`MV9107`). 실습이라 http(localhost) 사용 | 모의 기관 |
| 디자인 가이드의 버튼 규격(높이 64pt, 라운드 16pt) | 모의 화면 버튼의 높이와 라운드 값만 비슷하게 맞춤. **카카오뱅크 로고, 색상(#FFE300 등), 문구는 쓰지 않음** | 모의 화면 CSS |

## 8.3 의도적으로 다르게 한 것

| 항목 | 공개 가이드 | 실습 | 이유 |
|---|---|---|---|
| 결과코드 접두어 | `AC....` | `MV....` | 실제 기관 코드로 오해하지 않도록 |
| 접근토큰 위치 | 요청 Body의 `access_token` | `Authorization: Bearer` 헤더 | Body 로깅으로 토큰이 노출될 위험을 줄이려고 |
| 멱등 키 | 공개 가이드에는 명시적인 멱등 키가 없음 | `client_request_id`(서비스의 verificationId) 기준으로 멱등 | 응답 유실 후 재시도 시나리오를 다루려고 |
| 이용기관 취소 API | 공개 가이드에 없음 | `/cancel` 추가 | 서비스 화면에서 명시적으로 취소했을 때 기관 쪽 상태도 정리하려고 |
| 브랜딩 | 카카오뱅크 버튼과 로고 | 중립 색상과 "실습용 모의 인증" 배너 | 사칭이나 오해를 막으려고 |

## 8.4 실제 연동이라면 추가로 필요한 것 (이번 범위 밖)

- 제휴 계약, 이용기관 ID와 credential 발급, 방화벽(IP) 등록
- 요청과 결과의 개인정보 AES 암호화와 복호화. 키와 IV는 별도 채널로 받아 관리
- 결과 전자서명을 PKCS#7 형식 그대로 처리하고, CRL/OCSP로 폐지 여부 확인 (실습은 단순 형식이고 폐지 확인 없음)
- 콜백 수신 엔드포인트와 그 엔드포인트의 위변조 방지
- CI·DI를 받는다면 보관 근거, 암호화, 파기 정책, 그리고 계정 병합·중복 가입 정책에 대한 별도 기획
