# 40. 컴플라이언스 검토 (학습용 분석)

> **주의:** 개인 학습 목적의 분석이며 법률 자문이 아닙니다.
> - 조문 번호와 표제는 2026-11-02에 공개 자료를 검색해 확인했습니다. 실제로 도입한다면 국가법령정보센터 원문과 소관 부처 고시를 다시 확인하고 법무 검토를 받아야 합니다.
> - 이번 실습은 **실제 본인확인 서비스를 제공하지도, 이용하지도 않습니다.** 아래 내용은 "실제로 한다면 무엇을 지켜야 하고, 이번 설계가 어디까지 대비했는가"를 정리한 것입니다.

## 1. 관련 법령 지도

| 영역 | 법령 (조문) | 핵심 내용 | 이 기능과의 관계 |
|---|---|---|---|
| 주민등록번호 대체 | 정보통신망법 제23조의2 (주민등록번호의 사용 제한) | 정보통신서비스 제공자는 원칙적으로 이용자의 주민등록번호를 수집·이용할 수 없음 | 이 서비스는 주민등록번호를 받지 않고 외부 본인확인 수단을 씀 |
| 본인확인기관 | 정보통신망법 제23조의3 (본인확인기관의 지정) | 주민등록번호 대신 본인을 확인하는 수단을 제공하는 기관을 방송통신위원회가 지정 | 실제 연동은 **지정된 본인확인기관**과 해야 함. 공개 페이지에서 카카오뱅크는 자신을 본인확인기관이라고 밝힘 |
| 연계정보(CI) | 정보통신망법 제23조의5 (연계정보의 생성·처리 등, 2024년 신설) | CI 생성·처리의 근거와 절차 | 이번 설계는 CI를 **받지 않음**. 받는다면 처리 근거, 목적, 보관을 따로 설계해야 함. 이 조항을 두고 헌법소원이 제기됐다는 보도가 있음(결과는 확인하지 못함) |
| 주민등록번호 처리 | 개인정보 보호법 제24조의2 (주민등록번호 처리의 제한) | 법령 근거 등 예외가 아니면 처리 금지. **동의를 받아도 처리할 수 없음** | 수집하지 않음 |
| 최소 수집 | 개인정보 보호법 제16조 (개인정보의 수집 제한) | 목적에 필요한 최소한의 개인정보만 수집 | 기관에서 받는 값을 상태와 시각으로 한정. 이름·생년월일·전화번호도 받지 않음 |
| 파기 | 개인정보 보호법 제21조 (개인정보의 파기) | 보유기간이 지나거나 목적을 달성하면 지체 없이 파기 | 탈퇴하면 계정 확인 상태 초기화, 진행 중 요청 취소. **시도 이력의 보관 기간은 미정(오픈 이슈)** |
| 안전조치 | 개인정보 보호법 제29조 (안전조치의무) | 분실·도난·유출·위조·변조·훼손을 막는 기술적·관리적·물리적 조치(내부 관리계획, 접속기록 보관 등) | 감사 로그(개인정보 제외), 결과 위·변조 검증, 접근통제(본인 요청만 조회) |
| 전자서명 | 전자서명법 (2020-12-10 전부개정 시행) | 공인인증서 제도 폐지. 전자서명인증사업자는 **운영기준(제7조) 준수사실을 평가기관(제10조)에서 평가받고 인정기관(제9조, KISA)에서 인정(제8조)**받는 구조 | 인증 플랫폼 운영자가 받는 "라이선스 심사"의 법적 틀. [42](42-license-audit-readiness.md)에서 통제 항목으로 정리 |
| 전자금융 인증 | 전자금융거래법 제21조 (안전성의 확보의무) | 금융회사 등은 전자금융거래의 안전성을 확보해야 함. 인증방법 기준은 특정 기술을 강제하지 않도록 함 (2015년 감독규정 개정으로 공인인증서 사용의무 폐지 보도) | 인증서를 금융거래에 쓰는 이용기관이라면 감독규정상 인증방법 요건도 함께 검토해야 함 |

## 2. 설계 결정 ↔ 컴플라이언스 근거

| 설계 결정 | 근거·의도 | 구현 위치 |
|---|---|---|
| 주민등록번호·CI·DI를 받지 않음 | 개인정보 보호법 제24조의2, 제16조 / 정보통신망법 제23조의2 | `V1` 스키마, 연동 규격(개인정보 필드 없음) |
| 외부 결과를 서버가 직접 조회하고 서명을 검증 | 개인정보 보호법 제29조(위·변조 방지), 전자서명 신뢰 체계 | `ResultSignatureVerifier`, `verifyIntegrity` |
| 본인 요청만 조회(다른 회원은 404) | 접근통제(제29조 취지) | `findByVerificationIdAndUserId` |
| 감사 로그에 개인정보·토큰·서명값 없음 | 로그 자체가 개인정보 유출 경로가 되지 않도록 | `IdentityVerificationAuditLog` |
| 탈퇴 시 확인 상태 초기화, 진행 중 요청 취소 | 제21조(파기), 목적 달성 후 처리 중단 | `Member#withdraw`, WithdrawalCleaner |
| 등록된 callback URL만 허용 | 결과 화면 가로채기·오픈 리다이렉트 방지 | 모의 기관 `MV9107` |
| 실습 서버는 로컬 DB·로컬 모의 기관에만 연결 | 실제 신원 확인 없이 "확인 완료"가 운영 데이터에 생기는 것을 원천 차단 | `LabEnvironmentGuard` |
| 화면에 "실습용 모의 인증" 표시 | 사용자 오인 방지 | 모의 표준창 배너 |

## 3. 실제 도입 시 추가로 필요한 검토 (갭 분석)

| # | 항목 | 이번 상태 | 필요한 조치 |
|---|---|---|---|
| G1 | 본인확인기관 선정·계약 | 모의 기관 | 지정된 본인확인기관과 계약하고 기관 규격으로 연동 |
| G2 | 개인정보 처리방침, 수집·이용 동의 | 해당 없음(수집 없음) | 기관 표준창 동의와 서비스의 고지가 겹치거나 빠지지 않게 정리 |
| G3 | CI 수집 여부 결정 | 수집 안 함 | 중복 가입 방지 같은 목적이 생기면 근거(제23조의5 등), 암호화, 보관, 파기를 설계 |
| G4 | 시도 이력 보관 기간 | 미정 | 분쟁 대응 기간을 고려해 기간을 정하고 파기 배치 구현 |
| G5 | 전송 구간 보호 | HTTP(localhost) | TLS 1.2 이상, 서버 IP 방화벽 등록 |
| G6 | 결과 서명 형식 | 단순 서명 | 기관 규격(예: PKCS#7)을 따르고 인증서 폐지 확인(CRL/OCSP) |
| G7 | 키·credential 관리 | 설정 파일에 더미 값 | 비밀 관리 시스템(Vault 등), 접근권한, 교체 절차 |
| G8 | 접속기록 보관·점검 | 앱 로그 | 개인정보처리시스템 접속기록 보관과 정기 점검 체계 |
