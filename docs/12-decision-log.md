# 12. 의사결정 기록 (ADR)

각 결정은 맥락 → 선택지 → 결정 → 결과(트레이드오프) 순서로 적었습니다.

## ADR-01. 계정 상태와 시도 상태를 분리한다
- **맥락:** 본인확인은 여러 번 시도할 수 있고, 시도는 실패·취소·만료될 수 있습니다.
- **선택지:**
  - (a) 회원 테이블에 상태 하나만 둔다
  - (b) 계정 상태(2값)와 시도 테이블(5값)을 분리한다
- **결정:** (b)
- **결과:**
  - 실패한 시도가 계정에 영향을 주지 않는다는 규칙을 구조로 보장합니다.
  - 시도 이력이 남아 지표 M1~M3를 낼 수 있습니다.
  - 대신 테이블 1개와 상태 동기화 로직이 늘어납니다.

## ADR-02. 외부 결과 확인을 상태 조회 API(GET)에 포함한다
- **맥락:** 결과 확인을 별도 `/confirm`으로 둘지 고민했습니다.
- **결정:** GET 안에서 "PENDING이면 외부에 조회"합니다. 자세한 근거는 [04-api-spec.md §4.2](04-api-spec.md#42-설계-선택-외부-결과-확인을-상태-조회a2에-포함한-이유)에 있습니다.
- **결과:**
  - 앱 연동이 단순해집니다.
  - 클라이언트가 결과를 보낼 경로가 아예 없습니다.
  - 대신 GET의 응답 시간이 외부 기관에 의존합니다.

## ADR-03. 네트워크 오류를 실패로 단정하지 않는다
- **맥락:** 타임아웃이 나도 외부에서는 이미 성공했을 수 있습니다.
- **결정:** 의미가 확인된 응답만 종료 상태로 확정합니다. 그 밖에는 503을 응답하고 상태를 유지합니다. 유효시간과 유예시간(가정 10분)이 모두 지나야 만료로 확정합니다.
- **결과:**
  - 성공했는데 실패로 기록되는 오판을 막습니다.
  - 대신 장애가 길어지면 PENDING이 오래 남습니다. 지표 M5로 감시합니다.

## ADR-04. 판단 기준을 영역별로 나눈다 (외부 기관 vs 서비스)
- **결정:**
  - 사용자 행동(성공·실패·취소)은 외부 기관을 기준으로 합니다.
  - 유효시간, 확정된 상태, 계정 상태는 서비스를 기준으로 합니다.
  - 자세한 표는 [03 §3.3](03-policy-and-exceptions.md#33-판단-기준-모의-기관과-서비스-상태가-충돌할-때)에 있습니다.
- **결과:** 두 시스템의 상태가 어긋나도 어느 쪽을 따를지 미리 정해져 있습니다.

## ADR-05. 진행 중 요청은 회원당 1건, DB 부분 유니크 인덱스로 보장한다
- **선택지:**
  - (a) 애플리케이션에서 조회 후 생성
  - (b) 분산 락(예: Redis)
  - (c) DB 부분 유니크 인덱스
- **결정:** (a)를 기본으로 하고, (c)를 최종 방어선으로 둡니다. (b)는 쓰지 않습니다.
- **결과:**
  - 동시에 5번 요청해도 요청은 1건입니다(E2E S7).
  - 별도 락 저장소 없이 DB만으로 보장합니다.

## ADR-06. 외부 결과에 전자서명을 요구하고 요청 ID와 대조한다
- **맥락:** 이용기관이 결과를 서버 간 조회로 받더라도, 전송 구간 변조나 다른 거래의 결과가 섞여 들어오는 경우를 막아야 합니다. 참고한 공개 가이드도 결과에 `signed_data`(PKCS#7)를 붙입니다.
- **선택지:**
  - (a) TLS만 신뢰
  - (b) HMAC 공유키
  - (c) 공개키 서명과 인증서 체인
- **결정:** (c)
  - 기관이 자기 개인키로 서명하고, 서비스는 Root CA로 검증합니다.
  - 공유키 방식과 달리 서비스는 서명을 만들 수 없어서 부인 방지가 됩니다.
  - 기관이 서명 인증서를 교체해도 Root CA가 같으면 이용기관 쪽 설정을 바꿀 필요가 없습니다.
- **결과:**
  - PKI 운영(키 생성, 만료, 교체)이 필요합니다([41-pki.md](41-pki.md)).
  - CRL/OCSP 같은 폐지 확인은 이번 범위 밖입니다.

## ADR-07. 만료된 PENDING 정리 스케줄러는 이번에 만들지 않는다
- **맥락:** 사용자가 다시 조회하지 않으면 PENDING이 남습니다.
- **결정:** 구현하지 않습니다. 다음 조회나 요청 때 자동 확정되므로 기능상 문제가 없습니다. 운영 지표 M5로 감시합니다.
- **결과:** 지표 왜곡(PENDING 건수)이 생길 수 있습니다. 실제 도입 시 재검토합니다.

## ADR-08. 실습 기능을 실제 환경과 격리하고, 기동 단계에서 안전장치를 둔다
- **맥락:** 모의 기관·테스트 로그인처럼 "실제 신원 확인 없이 확인 완료를 만들 수 있는" 기능이 실제 환경에 섞이면 안 됩니다.
- **결정:**
  - 팀 서비스에 붙였을 때는 기능 코드를 `@Profile("lab")`으로 격리했습니다. 기존 보안 설정도 바꾸지 않고, 데모 화면 경로만 별도 필터 체인으로 공개했습니다 ([01 §1.2](01-origin-and-scope.md)).
  - 이 독립 저장소는 저장소 자체가 실습 전용입니다. 대신 `EnvironmentPostProcessor`로 **DB에 연결하기 전에** DB와 외부 기관 주소가 localhost인지 검사합니다.
- **결과:** 실수로 원격 DB나 실제 기관 주소를 가리키면 기동이 실패합니다(`LabEnvironmentGuardTest`).

## ADR-09. 다른 회원의 요청은 403이 아니라 404로 응답한다
- **결정:** `verificationId + userId`로 조회해서, 없으면 404를 응답합니다.
- **결과:** 다른 회원의 요청 ID가 존재하는지조차 알려주지 않습니다. 디버깅할 때 "왜 404인지"는 감사 로그로 확인합니다.

## ADR-10. 완료 시각은 서버가 확인·반영한 시각으로 한다
- **선택지:**
  - (a) 외부 기관의 `completed_dttm`
  - (b) 서버 반영 시각
- **결정:** 계정의 `identityVerifiedAt`은 (b)로 합니다. 외부 시각은 유효시간 판단에만 씁니다.
- **결과:** 외부 시계를 믿지 않아도 됩니다. 사용자가 실제로 인증한 시각과 몇 초 차이가 날 수 있습니다.
