# 10. 기획서 (PRD): 가입 후 선택형 본인확인

> 상태: 실습 구현 완료 · 작성: 개인 실습 (팀 프로젝트 합합의 공식 기획이 아님) · 기준일: 2026-11-02
> 가상 요구사항: *"가입 후 선택적으로 본인확인을 수행하고 계정에 확인 상태를 기록한다."*

## 1. 배경과 문제 정의

- 출발점이 된 서비스(합합)는 소셜 로그인만으로 가입합니다. 소셜 계정은 **"이 계정의 주인이 실제 사람 누구인지"를 보장하지 않습니다.**
- 이 서비스는 채용 결과(합격·불합격)를 공유합니다. 앞으로 아래 같은 기능을 고려한다면 **확인된 사람인지 여부**를 구분할 수 있어야 합니다(가정).
  - 신뢰도 표시
  - 보상(포인트) 남용 방지
  - 민감한 기능 접근 제한
- 그렇다고 가입 단계에서 본인확인을 강제하면 가입 이탈이 커집니다. 서비스 본질(정보 공유)과도 직접 관계가 없습니다.

**문제:** 가입 장벽을 높이지 않으면서도, 원하는 사용자는 본인확인을 마치고 그 사실을 계정에 신뢰할 수 있게 기록할 방법이 필요합니다.

## 2. 목표와 비목표

| 목표 | 비목표 (이번 범위 밖) |
|---|---|
| 가입·로그인 흐름을 바꾸지 않고 선택형 본인확인 진입점 제공 | 본인확인 여부로 기능 이용 제한 |
| 외부 인증기관 결과를 **서버가 직접 검증**해 계정 상태 기록 | 실제 본인확인기관·카카오뱅크 인증서 연동 |
| 실패·취소·만료·장애에도 계정 상태가 틀어지지 않는 일관성 | CI·DI 수집, 중복 가입 차단, 계정 병합 |
| 운영자가 상태와 원인을 추적할 수 있는 로그·지표 | 네이티브 앱 화면 구현 |
| 실습 환경 밖으로 모의 기능이 새지 않도록 차단 | 운영 배포 |

## 3. 이해관계자

| 이해관계자 | 관심사 | 이 기획이 답하는 방식 |
|---|---|---|
| 서비스 사용자 | 귀찮지 않을 것, 실패해도 손해가 없을 것 | 선택형. 실패해도 미확인 상태 그대로이고 기존 기능은 모두 사용 가능 |
| 앱 개발 | 화면 분기가 단순할 것 | API 3개, `status`와 `accountStatus` 두 필드로 분기 ([11-screens-and-copy.md](11-screens-and-copy.md)) |
| 서버·운영 | 장애에 강하고 원인을 추적할 수 있을 것 | 상태 기계, 감사 로그, 지표 SQL, 런북 ([30](30-api-operations-manual.md)) |
| 인증기관(제휴처) | 규격을 지키는 연동, 결과 위·변조 방지 | 연동 가이드·서명 검증·callback 등록제 ([20](20-partner-integration-guide.md)) |
| 법무·보안·개인정보 | 법령 준수, 최소 수집 | 식별정보 미수집, 컴플라이언스 검토 ([40](40-compliance-analysis.md)) |

## 4. 사용자 시나리오

| # | 시나리오 | 기대 결과 |
|---|---|---|
| US-1 | 신규 가입자가 가입 직후 "본인확인은 선택이에요" 안내를 보고 진행한다 | 성공하면 마이페이지에 '본인확인 완료'와 완료 시각 표시 |
| US-2 | 신규 가입자가 "나중에 할게요"를 누른다 | 서비스를 그대로 이용. 마이페이지에 '본인확인하기' 버튼 유지 |
| US-3 | 기존 회원이 마이페이지에서 '본인확인하기'를 누른다 | US-1과 같음 |
| US-4 | 인증 화면에서 취소하거나 실패한다 | "취소했어요/실패했어요" 안내. 계정은 미확인이고 다시 시도 가능 |
| US-5 | 인증 화면을 그냥 닫았다가 나중에 돌아온다 | 같은 요청으로 이어서 진행 (유효시간 안이라면) |
| US-6 | 인증은 성공했는데 앱으로 돌아오지 못했다 | 다음에 마이페이지에 들어와 버튼을 누르면 성공이 반영되고 '완료' 표시 |
| US-7 | 버튼을 여러 번 누른다 | 요청은 1건만 생김 |
| US-8 | 이미 확인한 회원이 다시 시도한다 | 이미 완료라는 안내 |

## 5. 기능 요구사항

| ID | 요구사항 | 우선순위 | 구현 |
|---|---|---|---|
| FR-1 | 본인확인 요청 생성 (진행 중이면 재사용) | 필수 | `POST /members/me/identity-verifications` |
| FR-2 | 진행 상태 조회와 외부 결과 확인 | 필수 | `GET .../{id}` |
| FR-3 | 명시적 취소 | 필수 | `POST .../{id}/cancel` |
| FR-4 | 내 정보에 계정 확인 상태와 완료 시각 노출 | 필수 | `GET /members/me` 필드 추가 |
| FR-5 | 로그인 응답 구조 유지, 로그인할 때마다 재확인하지 않음 | 필수 | `AuthResponse` 변경 없음 |
| FR-6 | 소셜 프로필(이름·이메일·전화번호)을 덮어쓰지 않음 | 필수 | 외부에서 해당 값을 받지 않음 |
| FR-7 | 탈퇴 시 진행 중 요청 취소, 계정 확인 상태 초기화 | 필수 | WithdrawalCleaner |
| FR-8 | 실습 전용 테스트 로그인·데모 화면 | 실습 | `TestLoginController`, `/lab/identity-demo` |

## 6. 비기능 요구사항

| ID | 요구사항 | 기준(실습 가정) | 검증 |
|---|---|---|---|
| NFR-1 | 신뢰: 클라이언트 값으로 성공 처리하지 않음 | 서버 간 조회 결과만 사용 | I `clientCannotClaimSuccess` |
| NFR-2 | 무결성: 외부 결과 위·변조와 다른 요청 결과 끼워넣기 차단 | 전자서명과 요청 ID 대조 | U 7개, E S8 |
| NFR-3 | 일관성: 종료 상태 역전 금지, 동시 처리 시 1회 반영 | 행 잠금 + PENDING 재확인 | I `concurrentFinalization` |
| NFR-4 | 가용성: 외부 장애가 실패로 처리되지 않음 | 503 + 상태 유지 + 재조회 복구 | E S4 |
| NFR-5 | 응답 시간: 상태 조회 최대 약 3초 | 외부 응답 타임아웃 3초 | E S4 (TIMEOUT) |
| NFR-6 | 보안 경계: 실습 서버가 실제 기관·운영 DB에 연결되지 않음 | localhost가 아니면 기동 중단 | U `LabEnvironmentGuardTest` |
| NFR-7 | 개인정보: 식별정보 미수집, 로그에 개인정보 없음 | 스키마·감사 로그 형식 | 코드 리뷰 |
| NFR-8 | 운영성: 원인 추적 가능 | 감사 로그 이벤트 7종, 지표 6종 | [30](30-api-operations-manual.md) |

## 7. 성공 지표 (KPI, 가정)

| 지표 | 정의 | 측정 |
|---|---|---|
| 본인확인 시도율 | 활성 회원 중 시도해 본 회원 비율 | `identity_verifications` 회원 수 ÷ 활성 회원 |
| 시도 성공률 | 성공 ÷ 시도 | 지표 M1 |
| 계정 확인 비율 | VERIFIED ÷ 활성 회원 | 지표 M4 |
| 이탈 원인 비중 | 종료 사유별 비율 | 지표 M2 |
| 소요 시간 | 성공까지 p50·p90 | 지표 M3 |
| 장애 영향 | `UNCONFIRMED_AFTER_EXPIRY` 건수 | 지표 M2 |

**지표를 읽는 법 예시:** `PROVIDER_USER_CANCELLED` 비율이 높다면 인증 화면 안내 문구나 단계를 의심합니다. `EXPIRED_BEFORE_COMPLETION`이 높고 p90이 5분에 가깝다면 유효시간이 짧다는 신호입니다.

## 9. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 외부 기관 장기 장애 | 사용자가 결과를 받지 못함 | 상태 유지, 유예 후 만료, 재시도 안내 |
| 결과 위·변조, 응답 바꿔치기 | 미인증 사용자가 확인 완료로 기록됨 | 서명 검증, 요청 ID 대조, callback 등록제 |
| 유효시간 설정이 맞지 않음 | 만료 이탈 증가 | M3로 주기 점검, 설정값 분리 |
| 모의 기능이 운영에 섞임 | 실제 신원 확인 없이 확인 완료 처리 | 프로필 분리, 기동 안전장치, 게이트 테스트 |
| 법령 해석 오류 | 규제 위반 | 컴플라이언스 검토 문서와 전문가 확인 (실제 도입 시) |

## 10. 오픈 이슈 (실제 도입 시 결정 필요)

1. 본인확인을 마친 회원에게 어떤 혜택이나 표시를 줄지(서비스 정책)
2. 시도 이력 보관 기간과 파기 주기
3. 어떤 본인확인 수단을 제공할지, 비용 구조는 어떤지
4. 같은 사람이 여러 계정에서 본인확인하는 경우 허용할지 (CI를 수집하지 않으면 구분할 수 없음)
5. 만료된 PENDING을 정리하는 스케줄러를 도입할지 (ADR-07)
